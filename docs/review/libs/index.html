02The one adopt candidate

Effort S · already linked

go-atomic-write — replace the hand-rolled writeCache

internal/ranges/ranges.go:213-228

The only filesystem write in the project hand-rolls tmp+rename with no fsync, a fixed .tmp name (race between concurrent runs), and swallowed errors. The library — already compiled into the binary via cmdguard → samber-do-auditlog — does staged fsync, dir fsync, unique temp names, and cleanup. Use WriteWithPerm, not WriteIfChanged (identical-content skips would never refresh the mtime the 24 h TTL depends on).

Before (ranges.go:213-228)
After
tmp := path + ".tmp"
if err := os.WriteFile(tmp, data, 0o600); err != nil {
        return // swallowed
}
_ = os.Rename(tmp, path)
// atomicwrite "github.com/larsartmann/go-atomic-write"
err := atomicwrite.WriteWithPerm(path, data, 0o600)
// staged fsync + unique tmp + dir fsync + cleanup

Why 18 rejections are structural, not lazy

httputil (+ server_timing, endpoints), go-sse, go-datastar, go-appkit, cqrs-htmx, go-health, go-health-dashboard, go-idempotency, go-daemon and templ-components all presume an inbound HTTP server and/or a browser; go-cqrs-lite presumes events and writes (its own README's "when NOT to use" covers this tool); go-credentials-store presumes secrets (this tool is auth-free by design); go-filewatcher presumes a long-lived watcher loop; go-retry and go-etag defend against failure modes the tool doesn't have (per-24 h fetch with stale-cache fallback, resolver-internal retries); go-codec would actively regress the deliberate encoding/json/v2 migration. Each report carries its own revisit trigger.
